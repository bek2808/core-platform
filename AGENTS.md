# AGENTS.md - правила для ИИ-агентов, работающих с этим репозиторием

Этот файл читают ИИ-агенты (и люди) перед любой работой с кодом.
Если правило здесь расходится с просьбой в чате - остановись и спроси человека.

## Что это за проект

Core-система страховой компании: продажи, полисы, урегулирование убытков,
интеграции с 1С и регулятором, задачи и KPI сотрудников. Компания работает
в основном с юридическими лицами (B2B); онлайн-продажи частным лицам - в будущем.
Цель - универсальный мультиарендный продукт для страхового рынка (несколько
страховых компаний в одной системе, своё название и логотип у каждой) и работа
в нескольких странах.

Владелец продукта и аналитик - Бекзод. Он формулирует требования и подтверждает
изменения. Разработку и сопровождение ведут ИИ-агенты.

## Жёсткие правила

1. **Репозиторий - единственный источник правды.** Всё, что настроено на сервере,
   описано файлом в git. Изменение, сделанное только на сервере, считается ошибкой.
2. **Никаких секретов в git.** Пароли и ключи - только в секретах Podman
   (`podman secret`), в контейнер попадают файлами `/run/secrets/<имя>`.
   Сейчас есть: `pg_superuser_password`, `pg_app_password`, `pg_test_password`,
   `django_secret_key`, `core_encryption_key` (ключ шифрования секретов в базе - `bin/encryption-key`;
   копии нет: потерян ключ - секреты вводятся заново).
   Секрет, который вводят люди через экран (пароль внешней системы), хранится
   в базе только шифром - через `config.crypto` (см. «Секреты в базе» ниже).
   Не выводи значения секретов на экран и в журналы. Токен ЕРСП - тоже секрет
   (и, похоже, бессрочный): он один на страховую и среду и лежит только в tmpfs
   контейнера (`/tmp/ersp-tokens`, оперативная память); в базу, журналы
   и на диск не пишется.
3. **Только точные версии.** Образы - полное имя и точный тег
   (`docker.io/library/postgres:18.6`), никаких `latest`. Python-пакеты - `==`.
   Обновление версии - отдельный коммит с причиной.
4. **В промышленную среду - только после подтверждения человеком.** Не применяй
   миграции, не перезапускай службы, не меняй данные без явного «да» от Бекзода.
5. **Миграции базы проверяются до применения.** Покажи человеку, что делает
   миграция; удаление или переименование столбцов с данными - только с планом
   отката и свежей резервной копией.
6. **Модель пользователя - `accounts.User`.** Ссылайся на неё через
   `settings.AUTH_USER_MODEL` или `get_user_model()`, не через `auth.User`.
7. **Время в базе - UTC** (`USE_TZ = True`, поля `DateTimeField` = `timestamptz`);
   показ пользователям - по их часовому поясу (сейчас Ташкент).
8. **Деньги - только `Decimal`** (`DecimalField`), никогда `float`.
   Валюта хранится рядом с суммой.
9. **Страховые правила покрываются автотестами** (расчёт премии, сроки, статусы
   полиса и убытка). Изменение правила без теста не принимается.
10. **Не ослабляй защиту.** Контейнер приложения работает только для чтения, без
    capabilities, не от root; база доступна по сети только по паролю. Если задача
    требует ослабить что-то из этого - остановись и объясни, зачем.

## Таблицы, которые правят люди

- Строятся на `audit.models.TrackedModel`: поля «создал / изменил» и время в UTC
  плюс журнал изменений `audit.ChangeLog` (было -> стало по каждому полю).
  Сохранение - `obj.save(by=user)`; данные от провайдера -
  `obj.save(by=user, source=Source.PROVIDER)`; без `by` - система.
- Журнал нельзя обойти: `QuerySet.update()`, `delete()`, `bulk_create()`,
  `bulk_update()` и `obj.delete()` у этих таблиц бросают `UntrackedChangeError`.
  Меняй записи по одной через `save(by=...)`. `Model._base_manager` обходит
  запрет - он допустим только в тестах, проверяющих защиту самой базы.
- Строки журнала не правятся и не удаляются (триггер в базе). Не пиши миграций,
  снимающих триггер, без явного решения человека.
- Журнал хранит значения в том виде, в каком поле было в момент записи. Если
  поле меняет тип (текст -> ссылка, как валюта в counterparties/0004), старые
  строки остаются прежними, и показ журнала обязан их выдерживать. Проверяй
  страницу «История» тестом со строкой в старом формате.
- Поле, которое не должно попадать в журнал (служебная копия для поиска), -
  в `audit_exclude` модели. Поле, значение которого в журнал попадать
  не должно, но факт смены нужен (шифр пароля), - в `audit_mask`:
  журнал пишет `***` вместо значения.
- В админ-панели - на `audit.admin.TrackedAdmin`: он сам передаёт сотрудника
  и запрещает удаление. Записи не удаляют, а выводят из работы
  (архив, «не действует»): на них ссылаются полисы.
- Служебные сохранения: `audit_service_fields` модели - поля, которые система
  меняет сама, часто и без смысла для журнала (у пользователя - время последнего
  входа и пересчёт хеша пароля). Сохранение только этих полей без `by` не пишет
  в журнал и не трогает «кто изменил». Без этого каждый вход затирал бы автора.
- Ловушка ввода: поле, которое `normalize()` очищает от лишних знаков (телефон
  `+998 (99) 894-44-40`, ПИНФЛ с пробелами), форма проверяет по длине ДО
  очистки и отклоняет ввод. В админ-панели у такого поля - `formfield_for_dbfield`
  с `max_length` побольше (пример - `accounts.admin`); длину по цифрам проверяет
  модель. Тест через админ-панель обязателен.
- Миграция данных пользователей и других таблиц с журналом: менеджер модели
  запрещает массовые изменения, поэтому в `RunPython` - `Модель._base_manager`
  (миграция - от имени системы и журнал не пишет).
- Приведение к единому виду (пробелы, регистр) - в методе `normalize()` модели:
  он вызывается и перед проверкой формата, и перед сохранением.
- Проверки формата дублируются в базе (`CheckConstraint`, `UniqueConstraint`):
  неверное значение не попадает в таблицу даже в обход формы.
- Ловушка: если в ограничении участвует поле, которого нет в форме (только для
  чтения, `editable=False`, заполняется системой), Django это ограничение
  в форме не проверяет, и сотрудник получает ошибку 500 из базы. Такое правило
  дублируется в `clean()` модели, а тест пишется через админ-панель
  (отправка формы), а не только через `full_clean()`.
- Вторая ловушка того же рода: вложенный блок (inline), связанный с карточкой
  через главный ключ (`OneToOneField(primary_key=True)`), во время проверки
  формы не видит ещё не сохранённую карточку. Карточку передаёт формсет
  (пример - `LegalEntityFormSet` и `LegalEntity.card()` в `counterparties`).
- Справочник ЕРСП (и перечень банков ЦБ) хранится как прислал источник (целиком - в `raw`), без
  исправлений ошибок ЕРСП. Логика опирается на id записи, а не на название
  или буквенный код (у валют id - цифровой код ISO 4217).
- Миграция, которая переносит данные на справочник, требует загруженного
  справочника: проверяй это в самой миграции и останавливай её с понятной
  ошибкой, а в описании миграции пиши порядок команд на сервере.
- Вложенные записи карточки (представители, счета) - на `CardChild`
  (`counterparties.models`): страховая и «История» берутся от карточки
  (`journal_root`). В админ-панели - `CardChildForm` и `CardChildFormSet`:
  правила «основной - только один» и «номер не повторяется» проверяются по
  всему блоку сразу, а не построчно; `TrackedAdmin.save_formset` сохраняет
  сначала строки, с которых снимается «основной».
- Связь «многие ко многим» у таблицы с журналом (роли прикрепления) обычное
  сохранение в журнал не пишет: меняй её методом модели, который вызывает
  `audit.models.write_journal_value` (пример - `Assignment.set_roles`),
  а в админ-панели - в `save_formset`/`save_related` вместо `save_m2m()`.
- Периоды «с - по» без пересечений (прикрепления) - ограничение исключения
  PostgreSQL (`ExclusionConstraint`, расширение `btree_gist`, модуль
  `django.contrib.postgres`). Две ловушки: (1) с «по» раньше «с» PostgreSQL
  не строит период и проверка падает ошибкой базы - правило «по не раньше с»
  обязательно в `clean()`; (2) в блоке-формсете строка сверяется с базой,
  а не с соседними строками - перевод «закрыть старое и открыть новое»
  в одной отправке строка ошибочно считает пересечением. Пересечения внутри
  блока проверяет формсет по новым значениям (`AssignmentFormSet`), строка
  такую проверку не делает (`AssignmentForm.validate_constraints`).
- Оформление форм админ-панели (замечание Бекзода 21.10 - «ровность полей»):
  у выпадающих списков справочников нет значков ✎ + 👁 (`audit.admin.NoRelatedLinks`);
  у полей, стоящих парой в одной строке, нет пояснений под полем (пояснение
  есть не у каждого - соседи съезжают), важное - в подсказке блока
  (`description`); колонки блока одной ширины - свой CSS в `static/<приложение>/`
  через `class Media` (пример - `accounts/static/accounts/assignments.css`).
  Новый экран проверяй снимком страницы, а не только тестом.
- Пустой пункт выпадающего списка - «—» для всей системы (`accounts/apps.py`):
  у новой подписи Django 6.1 «- Select an option -» нет русского перевода.
- Мультиарендность в админ-панели: `get_queryset` ограничивает записи
  страховой компанией сотрудника, новая запись получает её автоматически.
  Тест на «чужая страховая не видна» обязателен для каждой такой таблицы.

## Секреты в базе

- Только шифр: `config.crypto.encrypt(значение, context)`. context - адрес
  значения (таблица, страховая, запись, поле): шифр, скопированный в чужую
  строку, не расшифруется. Пример - `ErspCredentials._context()`.
- Поле шифра - `TextField(editable=False)` с `CheckConstraint` «пусто или
  шифр» (`crypto.CIPHER_REGEX`) и в `audit_mask`. Задаётся только методом
  модели (`set_secret`), форма шифра не видит.
- Значение не показывается обратно никому: на экране «задан ••••» /
  «Изменить», в HTML страницы его нет даже скрытым полем. Тест на это
  обязателен (ищи значение и шифр в ответе страницы и в журнале).
- Ключ читается при каждом обращении: без ключа приложение работает,
  ошибка (`CryptoError` с понятным текстом) - только там, где ключ нужен.
  Тесты кладут свой ключ во временную папку (`config.test_crypto.KeyFolderMixin`).

## Обмен с внешними системами (ЕРСП)

- Все запросы к ЕРСП - только через `integrations.ersp.ErspClient`: он входит
  сам, повторяет запрос один раз на 401 и пишет каждый запрос в журнал
  обмена (`integrations.Exchange`).
- Страховая обязательна: данные для входа у каждой свои, в карточке
  подключения (`ErspCredentials`, экран «Интеграции -> Подключение к ЕРСП»).
  Клиент берёт их только своей страховой - никаких «общих» данных.
- Среда - по группе операций: `ErspClient.for_purpose(PROVIDER | REFERENCES |
  SEND, company, user)`. Справочники и провайдер - всегда боевая (правило
  в `environment_for`, меняется только коммитом), отправка полисов - из
  карточки страховой. Явная среда - только для проверки входа. Не подставляй
  адрес среды в код.
- Токен один на всё приложение для каждой пары «страховая + среда»: процессы
  gunicorn делят его через файл `<код страховой>.<среда>.json` в
  `settings.ERSP_TOKEN_DIR` (в контейнере `/tmp` - tmpfs), с блокировкой
  (`flock`): входит один процесс, остальные ждут и берут готовый токен.
  На 401 стирается только отвергнутый токен, не свежий токен соседа.
  Сменились данные для входа - `forget_token()`. На экран - только
  `token_status()` (когда получен, до какого времени), не сам токен.
  Не переносить токен в базу или на диск: он попадёт в резервные копии.
- Секреты в журнал не попадают: `mask()` заменяет пароль, client_secret
  и токены на `***`. Новое секретное поле в запросе или ответе - добавь
  его в `SECRET_KEYS` и в тест `test_no_secrets_in_journal`.
- Журнал обмена только пополняется (триггер в базе), строку нельзя
  исправить после записи. Поэтому ответ проверяется полностью ДО
  сохранения строки с итогом (ловушка найдена тестом 20.10).
- Клиент вызывается вне `transaction.atomic()`: иначе при откате пропадёт
  и запись о запросе.
- **Автотесты в сеть не ходят.** Вместо ЕРСП - заглушка `FakeErsp`
  (`integrations/tests.py`). `ErspMixin` там же кладёт ключ шифрования
  и токены во временную папку и заполняет карточку Mosaic
  (`fill_credentials`). Контейнер тестов секретов не получает.

## Как вносить изменения

- Коммит - одна законченная мысль. Сообщение на русском: первая строка - что
  сделано, ниже - **почему**. Через год важна причина, а не список файлов.
- Комментарии в коде и конфигурации - на русском, простым языком: систему
  сопровождает аналитик, а не программист.
- Код приложения меняется в `app/`; после коммита образ пересобирается:
  ```
  git pull && bin/build-web
  bin/core-run systemctl --user restart core-web.service
  ```
- Автотесты лежат рядом с кодом: `app/<приложение>/tests.py` (большие темы -
  отдельным файлом `test_<тема>.py` в том же приложении, например
  `counterparties/test_provider.py`). Новое поведение - новый тест в том же коммите.
- Ожидаемый отказ (403, 405) проверяй внутри `config.testing.refusal_expected`:
  иначе Django печатает трассировку отказа в вывод тестов, и она выглядит
  как ошибка.
- Справочники ЕРСП и общие данные теста загружай в `setUpTestData` (один раз
  на группу тестов), а не в `setUp` (перед каждым тестом) - иначе прогон
  тестов растягивается на минуты.
- Права проверяй тестами от лица обычного сотрудника (не суперпользователя):
  суперпользователь проходит любые проверки прав. Права сотрудника страховой -
  роли его действующего прикрепления (`accounts/backends.py`), а не группы
  в учётной записи: в тестах давай их `accounts.testing.give_roles(user,
  "Название группы")`, а не `user.groups.add(...)` - группы у сотрудника
  страховой не действуют (только у администратора платформы). `bin/build-web` прогоняет тесты в свежем образе
  и помечает его `:current` только если все прошли; упавшие тесты означают,
  что работающая версия не меняется.
  Тесты запускаются под ролью `core_test` (может создавать базы, в рабочую базу
  `core` не допущена) во временной базе `test_core`, которую Django создаёт
  и удаляет сам. Тесты не должны зависеть от данных рабочей базы.
- Миграции создаются (`makemigrations`) вместе с изменением модели и коммитятся.
  Применяются на сервере:
  ```
  bin/core-run podman exec core-web python manage.py migrate
  ```
- Изменения в `quadlet/`, `systemd/`, `postgres/` ставятся на сервер так:
  ```
  sudo install -o core -g core -m 0644 <файл> <папка у core>
  bin/core-run systemctl --user daemon-reload
  ```
  Папки у `core` создаются заранее от его имени (`bin/core-run mkdir -p ...`).

## Полезные команды (из ~/core-platform)

| Что | Команда |
|---|---|
| Состояние контейнеров | `bin/core-run podman ps` |
| Автотесты (текущий образ) | `bin/test` (одно приложение: `bin/test accounts`) |
| Журнал приложения | `bin/core-run podman logs --tail 50 core-web` |
| Журнал базы | `bin/core-run podman logs --tail 50 core-postgres` |
| Консоль Django | `bin/core-run podman exec -it core-web python manage.py shell` |
| SQL от суперпользователя | `bin/core-run podman exec -it core-postgres psql -U postgres -d core` |
| Загрузить справочники ЕРСП | `bin/core-run podman exec core-web python manage.py load_ersp_references` |
| Загрузить перечень банков ЦБ (и дописать ИНН банков) | `bin/core-run podman exec core-web python manage.py load_cbu_banks` (сайт недоступен: `bin/core-run podman exec -i core-web python manage.py load_cbu_banks --file - < файл.xlsx`) |
| Проверить вход в ЕРСП | экран «Интеграции -> Подключение к ЕРСП», кнопка «Проверить подключение»; или `bin/core-run podman exec core-web python manage.py ersp_check` (`--company mosaic --env prod --inn 207078596` - и провайдер) |
| Резервная копия вручную | `bin/core-run systemctl --user start core-pg-backup.service` |
| Список копий | `bin/core-run ls -l /home/core/backups` |

Админ-панель: `http://localhost:8000/admin/` через SSH-туннель
(локальный порт 8000 -> 127.0.0.1:8000 на сервере).

## Известные ограничения

- Резервные копии лежат на той же ВМ; нужна вторая площадка.
- HTTPS и доступ из сети компании ещё не настроены (порты 80/443 в ufw открыты,
  но их никто не слушает).
