# AGENTS.md - правила для ИИ-агентов, работающих с этим репозиторием

Этот файл читают ИИ-агенты (и люди) перед любой работой с кодом.
Если правило здесь расходится с просьбой в чате - остановись и спроси человека.

## Что это за проект

Core-система страховой компании: продажи, полисы, урегулирование убытков,
интеграции с 1С и регулятором, задачи и KPI сотрудников. Компания работает
в основном с юридическими лицами (B2B); онлайн-продажи частным лицам - в будущем.
Цель - универсальный мультиарендный продукт для страхового рынка (несколько
страховых компаний в одной системе, своё название и логотип у каждой) и работа
в нескольких странах.

Владелец продукта и аналитик - Бекзод. Он формулирует требования и подтверждает
изменения. Разработку и сопровождение ведут ИИ-агенты.

## Архитектура

| Слой | Что | Где описано |
|---|---|---|
| ОС | Ubuntu 26.04 LTS, ВМ VMware, сервер 192.168.112.194 | - |
| Контейнеры | Podman 5.7 без root, пользователь `core` (UID 1001), управление через Quadlet | `quadlet/` |
| Сеть | `core-net` 10.89.10.0/24; контейнеры находят друг друга по имени | `quadlet/core.network` |
| База | PostgreSQL 18.6, контейнер `core-postgres`, база `core`, роль приложения `core_app` (не суперпользователь) | `quadlet/core-postgres.*`, `postgres/pg_hba.conf` |
| Приложение | Django 6.1 + gunicorn, контейнер `core-web`, порт 127.0.0.1:8000 | `app/`, `quadlet/core-web.container` |
| Резервные копии | `pg_dump` каждой базы, ежедневно 02:00 по Ташкенту, 14 дней | `bin/pg-backup`, `systemd/` |

Сейчас одна среда (будущая промышленная). Цель: разработка -> тест -> промышленная.

## Устройство репозитория

```
AGENTS.md                этот файл
app/                     Django-приложение (всё, что попадает в образ core-web)
  config/                настройки, адреса, точка входа WSGI
  accounts/              модель пользователя accounts.User
  Containerfile          рецепт образа
  requirements.txt       зависимости, только точные версии
  gunicorn.conf.py       настройки веб-сервера
  healthcheck.py         проверка живости для Podman
bin/                     скрипты для сервера (запускаются под support из ~/core-platform)
  core-run               выполнить команду от имени core
  build-web              собрать образ core-web из закоммиченного кода
  pg-backup              резервная копия (ставится в /home/core/.local/bin/)

systemd/                 служба и таймер резервного копирования

```

## Жёсткие правила

1. **Репозиторий - единственный источник правды.** Всё, что настроено на сервере,
   описано файлом в git. Изменение, сделанное только на сервере, считается ошибкой.
2. **Никаких секретов в git.** Пароли и ключи - только в секретах Podman
   (`podman secret`), в контейнер попадают файлами `/run/secrets/<имя>`.
   Сейчас есть: `pg_superuser_password`, `pg_app_password`, `django_secret_key`.
   Не выводи значения секретов на экран и в журналы.
3. **Только точные версии.** Образы - полное имя и точный тег
   (`docker.io/library/postgres:18.6`), никаких `latest`. Python-пакеты - `==`.
   Обновление версии - отдельный коммит с причиной.
4. **В промышленную среду - только после подтверждения человеком.** Не применяй
   миграции, не перезапускай службы, не меняй данные без явного «да» от Бекзода.
5. **Миграции базы проверяются до применения.** Покажи человеку, что делает
   миграция; удаление или переименование столбцов с данными - только с планом
   отката и свежей резервной копией.
6. **Модель пользователя - `accounts.User`.** Ссылайся на неё через
   `settings.AUTH_USER_MODEL` или `get_user_model()`, не через `auth.User`.
7. **Время в базе - UTC** (`USE_TZ = True`, поля `DateTimeField` = `timestamptz`);
   показ пользователям - по их часовому поясу (сейчас Ташкент).
8. **Деньги - только `Decimal`** (`DecimalField`), никогда `float`.
   Валюта хранится рядом с суммой.
9. **Страховые правила покрываются автотестами** (расчёт премии, сроки, статусы
   полиса и убытка). Изменение правила без теста не принимается.
10. **Не ослабляй защиту.** Контейнер приложения работает только для чтения, без
    capabilities, не от root; база доступна по сети только по паролю. Если задача
    требует ослабить что-то из этого - остановись и объясни, зачем.

## Как вносить изменения

- Коммит - одна законченная мысль. Сообщение на русском: первая строка - что
  сделано, ниже - **почему**. Через год важна причина, а не список файлов.
- Комментарии в коде и конфигурации - на русском, простым языком: систему
  сопровождает аналитик, а не программист.
- Код приложения меняется в `app/`; после коммита образ пересобирается:
  ```
  git pull && bin/build-web
  bin/core-run systemctl --user restart core-web.service
  ```
- Миграции создаются (`makemigrations`) вместе с изменением модели и коммитятся.
  Применяются на сервере:
  ```
  bin/core-run podman exec core-web python manage.py migrate
  ```
- Изменения в `quadlet/`, `systemd/`, `postgres/` ставятся на сервер так:
  ```
  sudo install -o core -g core -m 0644 <файл> <папка у core>
  bin/core-run systemctl --user daemon-reload
  ```
  Папки у `core` создаются заранее от его имени (`bin/core-run mkdir -p ...`).

## Полезные команды (из ~/core-platform)

| Что | Команда |
|---|---|
| Состояние контейнеров | `bin/core-run podman ps` |
| Журнал приложения | `bin/core-run podman logs --tail 50 core-web` |
| Журнал базы | `bin/core-run podman logs --tail 50 core-postgres` |
| Консоль Django | `bin/core-run podman exec -it core-web python manage.py shell` |
| SQL от суперпользователя | `bin/core-run podman exec -it core-postgres psql -U postgres -d core` |
| Резервная копия вручную | `bin/core-run systemctl --user start core-pg-backup.service` |
| Список копий | `bin/core-run ls -l /home/core/backups` |

Админ-панель: `http://localhost:8000/admin/` через SSH-туннель
(локальный порт 8000 -> 127.0.0.1:8000 на сервере).

## Известные ограничения

- Резервные копии лежат на той же ВМ; нужна вторая площадка.
- HTTPS и доступ из сети компании ещё не настроены (порты 80/443 в ufw открыты,
  но их никто не слушает).
- Автотесты Django пока не запускаются: роли `core_app` нельзя создавать
  тестовую базу. Решение - отдельный этап.
