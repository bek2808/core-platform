# Пользователи, подразделения, агенты: требования

Записано по разговору 21.10.2026: вопросы задавал Claude, ответы — Бекзода
(близко к его словам). Это требования, а не модель данных: модель
проектируется по ним отдельно (будет `docs/users-model.md`) и согласуется
с Бекзодом до кода.

## Исходная картина

- В Mosaic филиалов нет, официальных подразделений тоже. Сотрудники работают
  по направлениям, которые можно разнести по отделам. На сайте компании
  (mosaicinsurance.uz/ru/team) 11 человек: генеральный директор, заместитель,
  главный бухгалтер, внутренний аудитор, директор по коммерческому
  и потребительскому страхованию, андеррайтер по коммерческим линиям,
  менеджеры (коммерческие линии; здоровье и жизнь; расчёт портфеля
  и резервов; претензии; страхование). На сайте не все: есть ассистенты
  у менеджера страхования здоровья и жизни, у менеджера по коммерческим
  линиям, у директора по коммерческому и потребительскому страхованию;
  бизнес-аналитик (Бекзод); программист 1С — внештатный.
- В Inson (прежняя компания Бекзода) есть филиалы; в филиале и в головном
  офисе бывают подразделения; подразделений внутри подразделений не было.
- Система — продукт для разных страховых, поэтому должна подходить обеим
  моделям.

## Подразделения

- Виды: головной офис, филиал, отдел. Вложенность — не больше двух уровней:
  отдел внутри головного офиса или филиала.
- В Mosaic отделы заводим, и видимость строится по ним (решение Бекзода).
- У подразделения есть код — он входит в номер договора. Пример Inson:
  `0101/1403/26/0001` — 0101 код филиала (здесь головной офис), 1403 код
  продукта (автокредит), 26 год заключения, 0001 порядковый номер.
  У Mosaic свои правила номера — ещё не изучены; сейчас в 1С номер вводят
  вручную, цель — формировать автоматически, без ошибок. Сам номер
  договора — вместе с полисами; код подразделения закладывается сейчас.

## Люди

- Виды: штатные сотрудники, работники по ГПХ, агенты — физлица и юрлица.
- Каждый в каждый момент времени — ровно в одном месте (одно подразделение,
  одна роль). Совместительства (два отдела, сотрудник и агент сразу) нет.
- Прикрепление к подразделению — с историей (с какой даты, по какую):
  при переводе (в т. ч. агента между филиалами и головным офисом) видно,
  где человек был на дату каждого договора — от этого зависит номер договора.
- Увольнение или конец соглашения: учётная запись блокируется, не удаляется;
  договоры остаются за человеком (история, KPI). Нужен механизм передачи
  его «портфеля» другому (например, кто ведёт пролонгации его клиентов):
  выборочно — отмеченные договоры, или всем списком (ответ 21.10).

## Агенты

- Цель: агент сам вводит свои продажи. Сейчас в 1С вместо агентов продажи
  вносят сотрудники.
- Агент — контрагент из справочника (юрлицо: ИНН, счёт для комиссии,
  директор; физлицо: ПИНФЛ, паспорт) плюс соглашение плюс пользователи
  для входа.
- Соглашение с агентом заключает головной офис (в Mosaic — генеральный
  директор), директор филиала или сотрудник с доверенностью на это
  (может быть и работник по ГПХ в филиале, а не штатный директор).
  В соглашении — кто подписал со стороны страховой и по какой доверенности.
- Агент продаёт только разрешённые ему продукты. По каждому продукту —
  процент комиссии и лимит (например, по страховой сумме); пределы
  задаёт законодательство.
- Агент-юрлицо: каждый его сотрудник входит под своим логином. Директор
  агента видит все продажи агентства, закреплённые сотрудники — только свои.

## Видимость и права

- Сотрудник видит своё, руководитель — своё подразделение, администратор
  страховой — всё в своей страховой.
- Ассистент работает за менеджера: вводит договоры, которые продал
  менеджер. В договоре различаются «кто продал» (за кем продажа и KPI)
  и «кто ввёл». Что видит ассистент — настраивается выборочно: все договоры
  своего менеджера или только введённые им (ответ 21.10).
- Руководителем подразделения может быть и работник по ГПХ (ответ 21.10).
- Администратор страховой: заводит пользователей и подразделения своей
  страховой (только своей), сбрасывает пароли, блокирует уволенных;
  доступ ко всем данным своей страховой.
- Общий администратор всех страховых (владелец платформы): по умолчанию
  только управление — заводить страховую и её администратора, смотреть
  состояние; доступа к договорам и клиентам страховых нет. Доступ к данным —
  только по явному разрешению страховой и с записью в журнал. Как удобно
  показать ему всё (сначала список страховых, внутри пользователи, или
  фильтры для мониторинга) — продумать.

## Вход

- Агенты работают не из офиса: системе нужен доступ из интернета (имя
  в интернете и настоящий сертификат), а не только из сети компании.
- Второй шаг при входе — для всех; код в Telegram, у кого нет Telegram —
  по SMS (ответ 21.10).
- Цель в идеале — государственная идентификация, два сервиса с разной ролью
  (ответ 21.10):
  - MyID — подтверждение учётной записи: при подключении человек вводит
    паспортные данные и проходит распознавание лица (FaceID);
  - OneID (id.egov.uz) — способ входа: пользователь там уже подтверждён.
    Входить через OneID можно, только если в системе уже есть его учётная
    запись (её завели заранее) — самостоятельной регистрации нет. Для
    сопоставления у пользователя хранится ПИНФЛ.
- Для начала — несколько способов на выбор: телефон и пароль, код по SMS,
  код в Telegram, логин и пароль, почта и пароль.

## Открытые вопросы (для проектирования)

- Роли и наборы прав внутри страховой — универсальные, чтобы подходили
  любому страховщику (ответ 21.10). Названия в разговоре (продавец,
  андеррайтер, урегулировщик, бухгалтер, актуарий, руководитель) — только
  примеры по должностям с сайта Mosaic; состав ролей и действия — решить
  при проектировании.
- Правила номера договора Mosaic — в конце, вместе с полисами; до тех пор
  допустим ручной ввод номера (ответ 21.10).
- Условия подключения MyID и OneID (договор, технические требования);
  отправка SMS — через какого оператора.
