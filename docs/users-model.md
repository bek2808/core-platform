# Пользователи, подразделения, роли: модель данных

**Черновик 21.10.2026, на согласовании с Бекзодом. Кода по нему ещё нет.**
Основа — требования `docs/requirements/users-structure.md` (разговор 21.10).
После согласования ответы на вопросы в конце вписываются сюда, и этот файл
меняется в том же коммите, что и модель.

## Главные принципы

- **Одна схема для любой страховой.** Головной офис есть всегда; филиалы
  и отделы — по желанию. Mosaic: головной офис и отделы в нём. Inson:
  головной офис, филиалы, отделы в них. Глубже двух уровней не бывает.
- **Место человека — с историей.** Где работал, в какой должности, с какой
  даты и по какую — отдельная таблица «Прикрепления». На любую дату у человека
  ровно одно действующее прикрепление; это проверяет сама база.
  Перевод — закрыть старое прикрепление, открыть новое; старое не правится.
- **Права = набор ролей, видимость = отдельная настройка.** Роль отвечает
  на вопрос «что человек может делать» (оформлять договоры, урегулировать
  убытки, заводить пользователей). Видимость — «чьи данные он видит»:
  свои / своего подразделения / всей страховой. Роли общие для всех
  страховых и задаются платформой (миграциями), страховая их только назначает.
- **Ничего не удаляем.** Уволили — учётная запись блокируется, прикрепление
  закрывается датой; договоры остаются за человеком. Подразделение
  закрывают, а не удаляют.
- **Владелец платформы не видит данных страховых.** Он заводит страховые
  и их администраторов и смотрит состояние; клиенты и договоры ему
  не показываются. Доступ к данным — позже, по разрешению страховой
  и с записью в журнал.
- **Всё, что правят люди, — в журнале изменений** (`TrackedModel`):
  кто завёл пользователя, кто заблокировал, кто перевёл.

## Структура (как это выглядит)

```
Страховая компания (companies.InsuranceCompany)  — есть
 └─ Подразделение: головной офис     (ровно один, создаётся вместе со страховой)
     ├─ Подразделение: отдел
     └─ ...
 └─ Подразделение: филиал            (сколько угодно, может не быть)
     └─ Подразделение: отдел

Пользователь (accounts.User)  — есть, дополняется
 └─ Прикрепление (с даты — по дату): подразделение, должность, роли, руководитель ли,
                                     чей ассистент
```

## Таблицы

### Подразделение (`companies.Department`, новая, TrackedModel)

| Поле | Что | Правило |
|---|---|---|
| страховая | `InsuranceCompany` | обязательна, не меняется |
| вид | головной офис / филиал / отдел | не меняется после создания |
| входит в | подразделение-родитель | у головного офиса и филиала — пусто; у отдела — обязательно головной офис или филиал **своей** страховой |
| название | текст | обязательно |
| код | цифры | для номера договора; см. вопрос 5 |
| регион | регион ЕРСП | для филиала; см. вопрос 5 |
| статус | действует / закрыто | закрыть нельзя, пока в нём есть действующие прикрепления или открытые отделы |

Проверки в базе: один головной офис на страховую; код не повторяется
внутри страховой; у отдела есть родитель, у остальных нет. Правило «отдел —
только внутри головного офиса или филиала» проверяет модель (`clean()`)
и тест через админ-панель (ловушка из AGENTS.md: в форме нет поля родителя
другого вида).

Головной офис создаётся миграцией для каждой существующей страховой
и автоматически — для новой.

### Пользователь (`accounts.User`, дополняется)

Сейчас: логин, имя, фамилия, e-mail, пароль, «активен», страховая.

| Новое поле | Что |
|---|---|
| отчество | для ФИО полностью |
| вид | штатный сотрудник / работник по ГПХ / агент / платформа |
| телефон | с кодом страны, как у контрагентов (`998...`); для входа по телефону и SMS — этап «Вход» |
| ПИНФЛ | 14 цифр; для сопоставления с OneID — этап «Вход» |

- «Статус персонала» (`is_staff`, пускает в админ-панель) больше не ставят
  руками: его выставляет система — да для штатных, ГПХ и платформы, нет
  для агентов (у агентов будет свой кабинет, не админ-панель).
- «Активен» снят — учётная запись заблокирована (увольнение, конец
  соглашения). Войти нельзя, договоры и история остаются.
- Пользователь переводится на `TrackedModel`: в журнал пишется, кто завёл,
  заблокировал, сменил данные. Пароль — только факт смены (`audit_mask`),
  время последнего входа — не пишется (`audit_exclude`).
- Страховая у пользователя не меняется после создания. Человек перешёл
  в другую страховую — это новая учётная запись в ней.

### Роль (`accounts.Role`, новая, только чтение для людей)

Роль = группа прав Django (`auth.Group`) плюс описание. Каталог ролей один
на платформу, заводится миграцией; администратор страховой роли только
назначает, состав прав не меняет.

| Поле | Что |
|---|---|
| группа прав | `auth.Group`, один к одному |
| код | латиница, не меняется (`sales`, `claims`, ...) |
| для кого | сотрудники страховой / агенты / платформа |
| видимость по умолчанию | свои / подразделение / вся страховая |
| описание | что умеет, простыми словами |

Предлагаемый каталог (вопрос 1). Действия по договорам и убыткам появятся
вместе с этими модулями; сейчас роль заводится, права в неё добавляются
миграцией каждого модуля.

| Роль | Что делает | Видимость по умолчанию | Есть сейчас |
|---|---|---|---|
| Продажи | оформляет договоры, ведёт своих клиентов | свои | — |
| Андеррайтинг | согласует нестандартные условия, тарифы | вся страховая | — |
| Урегулирование убытков | заявления, расчёт, выплаты по убыткам | вся страховая | — |
| Бухгалтерия | оплаты, комиссии агентов, сверки | вся страховая | — |
| Актуарий и отчётность | только чтение всего, резервы, выгрузки | вся страховая | — |
| Контроль (аудитор) | только чтение всего и журналов | вся страховая | — |
| Администратор справочников | контрагенты, банки, должности | вся страховая | группа есть |
| Администратор интеграций | подключение к ЕРСП | вся страховая | группа есть |
| Сотрудник (базовая) | просмотр справочников | вся страховая | группа есть |
| **Администратор страховой** | пользователи, подразделения, блокировка, сброс пароля — только своя страховая | вся страховая | — |
| Агент | продажи разрешённых продуктов | свои | этап «Агенты» |
| Директор агента | плюс продажи всего агентства | агентство | этап «Агенты» |
| **Администратор платформы** | страховые и их администраторы, состояние; данных страховых не видит | — | — |

### Прикрепление (`accounts.Assignment`, новая, TrackedModel)

Где и кем человек работает с какой даты по какую.

| Поле | Что | Правило |
|---|---|---|
| пользователь | `User` | обязательно |
| подразделение | `Department` | той же страховой, что пользователь; действующее на дату начала |
| должность | текст (из списка должностей, вопрос 6) | обязательно |
| роли | одна или несколько ролей «для сотрудников страховой» | вопрос 2 |
| руководитель подразделения | да / нет | на дату — не больше одного руководителя на подразделение (проверка в базе) |
| видимость | свои / подразделение / вся страховая | по умолчанию — самая широкая из ролей; руководитель — не уже подразделения |
| ассистент для | другой пользователь (менеджер) | пусто — не ассистент |
| ассистент видит | все договоры менеджера / только введённые им | только если указан менеджер |
| действует с | дата | обязательно |
| действует по | дата включительно | пусто — по сей день |
| основание | текст (приказ, соглашение ГПХ) | необязательно |

Проверки в базе: «по» не раньше «с»; периоды одного пользователя
не пересекаются (ограничение исключения PostgreSQL на диапазон дат,
расширение `btree_gist` — см. «Проверить на сервере»); у руководителей
одного подразделения периоды не пересекаются; «ассистент видит» заполнено
тогда и только тогда, когда указан менеджер.

Действия на экране:
- **Перевести** — дата перевода, новое подразделение, должность, роли:
  старое прикрепление закрывается накануне, новое открывается с даты.
- **Уволить / завершить** — дата: прикрепление закрывается, учётная
  запись блокируется. Передача портфеля — вместе с договорами.
- Прикрепление, по которому уже есть договоры, не правится — только
  закрывается (появится вместе с договорами).

Права пользователя берутся из ролей **действующего сегодня** прикрепления
(свой способ проверки прав, `accounts.backends`), а не из групп в карточке
пользователя: перевод сразу меняет права, история ролей сохраняется.
Нет действующего прикрепления — нет прав (кроме платформы).

## Видимость данных

Одна функция для всех таблиц страховой: «что из этого видит пользователь».

| Кто | Видит |
|---|---|
| видимость «вся страховая» | всё своей страховой |
| видимость «подразделение» | своё подразделение; для филиала — с его отделами |
| видимость «свои» | записи, где он продавец или ввёл их |
| ассистент | плюс договоры своего менеджера (все или введённые им — по настройке) |
| администратор платформы | ничего из данных страховых |
| суперпользователь | всё (аварийная техническая запись, вопрос 4) |

Сейчас действует только первая строка и последние две: договоров ещё нет,
а справочник контрагентов виден всей страховой (вопрос 3). Нынешние
`own_companies` и `get_queryset` в админ-панелях переходят на эту функцию.

## Администратор страховой и администратор платформы

**Администратор страховой** в админ-панели:
- видит и заводит пользователей и подразделения только своей страховой;
  новая запись получает его страховую сама;
- назначает только роли «для сотрудников страховой»; роли платформы,
  «суперпользователь» и чужую страховую выбрать нельзя;
- блокирует, сбрасывает пароль, переводит;
- не может заблокировать или лишить роли последнего администратора своей
  страховой (иначе страховая останется без управления).

**Администратор платформы** (вид «платформа», без страховой, не суперпользователь):
- экран «Страховые компании»: список со счётчиками — пользователей
  (действующих / заблокированных), подразделений, последний вход в страховой;
  из строки — ссылка «Пользователи (N)» на список пользователей этой страховой;
- в списке пользователей — фильтр по страховой, виду, статусу, роли;
- заводит страховую (вместе с головным офисом) и её первого администратора;
- контрагенты, журнал обмена, журнал изменений данных страховых — пусто
  (так работает уже сейчас для пользователя без страховой и без
  «суперпользователя»; закрепим тестом).

Тесты на каждое правило — от лица обычного администратора страховой,
не суперпользователя: «чужая страховая не видна», «нельзя назначить роль
платформы», «нельзя сделать суперпользователем», «последний администратор».

## Перенос того, что уже есть (миграция данных)

1. Каждой страховой — головной офис (название «Головной офис», код — по ответу
   на вопрос 5).
2. Пользователю со страховой — вид «штатный», прикрепление к головному
   офису с даты регистрации, должность — «не указана», роли — по его
   нынешним группам. Бекзоду — плюс «Администратор страховой».
3. Три нынешние группы становятся ролями; группы и их права не меняются.
4. Пользователь без страховой — вид «платформа» (суперпользователь
   остаётся суперпользователем).

Миграция обратима до появления договоров. Перед применением — резервная копия.

## Порядок работ

Этот шаг (A) — по частям, каждая со своими тестами и сборкой:

| Часть | Что |
|---|---|
| A1 | Подразделения: таблица, головной офис, экран, «чужая страховая не видна» |
| A2 | Пользователь: новые поля, журнал, роли, прикрепления с историей, права по прикреплению, перенос существующих |
| A3 | Администратор страховой: ограничения, перевод и увольнение, «последний администратор» |
| A4 | Администратор платформы: экран страховых со счётчиками, фильтры |

Дальше, отдельными шагами:
- **B. Агенты** — агент (контрагент + соглашение: номер, дата, срок,
  кто подписал, доверенность), подразделение агента с историей, пользователи
  агента, директор агента. Агенту-физлицу нужна карточка физлица —
  её ещё нет (этап «Физлица»).
- **C. Вход** — доступ из интернета (имя и сертификат), второй шаг
  кодом в Telegram / по SMS, вход по телефону и почте, затем OneID и MyID.
  Тогда же — правила уникальности телефона и ПИНФЛ между страховыми
  (агент может работать с несколькими страховыми).
- **Вместе с продуктами и договорами** — разрешённые агенту продукты,
  комиссия и лимиты; «кто продал» и «кто ввёл» в договоре; передача
  портфеля; номер договора по коду подразделения; разрешение страховой
  на доступ владельца платформы к данным.

## Проверить на сервере до кода

- Может ли роль `core_app` включить расширение `btree_gist`
  (`CREATE EXTENSION`): с PostgreSQL 13 оно «доверенное», владельцу базы

  Если нет — правило «периоды не пересекаются» останется только в коде

## Вопросы Бекзоду

Ответы впишутся в эту модель. У каждого — предложение по умолчанию.

1. **Каталог ролей** (таблица выше) — подходит? Что убрать или добавить?
2. **Одна роль или несколько.** В требованиях: «одна роль в каждый момент».
   Но права уже разбиты по участкам (справочники, интеграции), и в маленькой
   страховой один человек часто совмещает: Бекзод — аналитик, администратор
   страховой и справочников. *Предложение:* место одно (одно подразделение,
   одна должность), а ролей у прикрепления может быть несколько.
3. **Справочник контрагентов (клиенты).** *Предложение:* сотрудники страховой
   видят всю клиентскую базу своей страховой, как сейчас; агенты — только
   клиентов своих договоров. Или продавец тоже должен видеть только своих?
4. **Суперпользователь.** *Предложение:* у Бекзода две учётные записи —
   «администратор страховой» в Mosaic для ежедневной работы и
   «администратор платформы» без доступа к данным. Суперпользователь
   остаётся аварийной технической записью (видит всё, заводится только
   командой на сервере), в ежедневной работе не используется. Согласны?
5. **Код подразделения.** Есть ли код у отдела или только у головного
   офиса и филиала (в примере Inson `0101` — код филиала)? Формат —
   только цифры, сколько знаков? *Предложение:* код у всех видов, 2–6 цифр,
   не повторяется внутри страховой; номер договора возьмёт код того уровня,
   какой задаст правило страховой. И нужен ли филиалу регион ЕРСП?
6. **Должность.** *Предложение:* свой список должностей страховой
   (у каждой свой, администратор страховой пополняет), а не общий справочник
   должностей представителей контрагентов.
7. **Отделы Mosaic.** Какие заводим на старте? Например: руководство,
   коммерческое страхование, страхование здоровья и жизни, урегулирование
   убытков, бухгалтерия, актуарный отдел, ИТ и аналитика. Можно завести
   и позже через экран.
8. **Работник по ГПХ** — отличается от штатного чем-то кроме отметки
   (права, отчёты, срок соглашения)? *Предложение:* только отметка
   и основание (соглашение) в прикреплении.
