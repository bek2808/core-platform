## Главные принципы

- **Одна схема для любой страховой.** Головной офис есть всегда; филиалы
  и отделы — по желанию. Mosaic: головной офис и отделы в нём. Inson:
  головной офис, филиалы, отделы в них. Глубже двух уровней не бывает.
- **Место человека — с историей.** Где работал, в какой должности, с какой
  даты и по какую — отдельная таблица «Прикрепления». На любую дату у человека
  ровно одно действующее прикрепление; это проверяет сама база.
  Перевод — закрыть старое прикрепление, открыть новое; старое не правится.
- **Права = набор ролей, видимость = отдельная настройка.** Роль отвечает
  на вопрос «что человек может делать» (оформлять договоры, урегулировать
  убытки, заводить пользователей). Видимость — «чьи данные он видит»:
  свои / своего подразделения / всей страховой. Роли общие для всех
  страховых и задаются платформой (миграциями), страховая их только назначает.
- **Ничего не удаляем.** Уволили — учётная запись блокируется, прикрепление
  закрывается датой; договоры остаются за человеком. Подразделение
  закрывают, а не удаляют.
- **Владелец платформы не видит данных страховых.** Он заводит страховые
  и их администраторов и смотрит состояние; клиенты и договоры ему
  не показываются. Доступ к данным — позже, по разрешению страховой
  и с записью в журнал.
- **Всё, что правят люди, — в журнале изменений** (`TrackedModel`):
  кто завёл пользователя, кто заблокировал, кто перевёл.

## Структура (как это выглядит)

```
Страховая компания (companies.InsuranceCompany)  — есть
 └─ Подразделение: головной офис     (ровно один, создаётся вместе со страховой)
     ├─ Подразделение: отдел
     └─ ...
 └─ Подразделение: филиал            (сколько угодно, может не быть)
     └─ Подразделение: отдел

Пользователь (accounts.User)  — есть, дополняется
 └─ Прикрепление (с даты — по дату): подразделение, должность, роли, руководитель ли,
                                     чей ассистент
```

## Таблицы

### Подразделение (`companies.Department`, новая, TrackedModel)

| Поле | Что | Правило |
|---|---|---|
| страховая | `InsuranceCompany` | обязательна, не меняется |
| вид | головной офис / филиал / отдел | не меняется после создания |
| входит в | подразделение-родитель | у головного офиса и филиала — пусто; у отдела — обязательно головной офис или филиал **своей** страховой |
| название | текст | обязательно |
| код | цифры, 2–6 знаков | необязателен у всех видов (в Mosaic кодов нет, в Inson есть); если задан — не повторяется внутри страховой. Входит в номер договора по правилу страховой |
| регион | регион ЕРСП | у филиала обязателен; у головного офиса — регион страховой (`InsuranceCompany.ersp_region`); у отдела — регион родителя. У головного офиса и отдела поля нет, система берёт регион сама |
| статус | действует / закрыто | закрыть нельзя, пока в нём есть действующие прикрепления или открытые отделы |

Проверки в базе (`companies/0002_department`): один головной офис на страховую; заданный код не повторяется
внутри страховой; у филиала есть регион; у отдела есть родитель, у остальных нет. Правила, которые смотрят на другую
строку (отдел входит только в головной офис или филиал **своей** страховой;
страховая, вид и «входит в» не меняются после создания), — триггером
`companies_department_rules`. Все правила продублированы в `clean()`
модели: страховой в форме нет, поэтому без этого сотрудник получил бы
ошибку 500 вместо сообщения (ловушка из AGENTS.md).

Реорганизация — закрыть подразделение и завести новое: если бы отдел
можно было перенести в другой филиал, история прикреплений перестала бы
показывать, где человек был на дату договора. Закрыть нельзя головной
офис и подразделение с действующими отделами; в закрытое нельзя добавить
отдел. Два действующих подразделения с одним названием (без учёта
регистра) в одном месте не бывает.

Права (`companies/0003_department_access`): новая группа «Администратор
страховой» — заводит и правит подразделения своей страховой; группа
«Сотрудник» — видит их.

Головной офис создаётся миграцией для каждой существующей страховой
и автоматически — для новой.

### Пользователь (`accounts.User`, дополняется)

Сейчас: логин, имя, фамилия, e-mail, пароль, «активен», страховая.

| Новое поле | Что |
|---|---|
| отчество | для ФИО полностью |
| вид | штатный сотрудник / работник по ГПХ / агент / платформа |
| телефон | с кодом страны, как у контрагентов (`998...`); для входа по телефону и SMS — этап «Вход» |
| ПИНФЛ | 14 цифр; для сопоставления с OneID — этап «Вход» |

- «Статус персонала» (`is_staff`, пускает в админ-панель) больше не ставят
  руками: его выставляет система (`User.normalize`, с A2.3) — да для штатных,
  ГПХ и платформы, нет для агентов (у агентов будет свой кабинет, не
  админ-панель). Что человек в админ-панели видит — решают роли.
- «Активен» снят — учётная запись заблокирована (увольнение, конец
  соглашения). Войти нельзя, договоры и история остаются.
- Пользователь переведён на `TrackedModel` (A2.1): в журнал пишется, кто
  завёл, заблокировал, сменил данные. Пароль — только факт смены
  (`audit_mask`). Вход пользователя (время последнего входа) и пересчёт хеша
  пароля при входе — «служебные сохранения» (`audit_service_fields`): в журнал
  не пишутся и не затирают «кто изменил».
- Телефон — цифры (7–15), ПИНФЛ — 14 цифр; проверяются в коде и в базе.
  Уникальность телефона и ПИНФЛ — в этапе «Вход» (агент может работать
  с несколькими страховыми).
- Вид «платформа» — только без страховой (проверка в базе); остальные виды —
  со страховой (проверка в `clean()`; исключение — аварийный суперпользователь).
- Страховая у пользователя не меняется после создания (триггер в базе
  `accounts_user_company_fixed`; где она была пуста — задать один раз можно).
  Человек перешёл в другую страховую — это новая учётная запись в ней.
- Экран «Пользователи»: пользователь страховой видит и заводит только своих;
  не суперпользователь не видит и не меняет «суперпользователь», группы
  и отдельные права (иначе мог бы повысить права себе) и не может назначить
  вид «администратор платформы».

### Роль (`accounts.Role`, новая, только чтение для людей)

Роль = группа прав Django (`auth.Group`) плюс описание. Каталог ролей один
на платформу, заводится миграцией; администратор страховой роли только
назначает, состав прав не меняет.

| Поле | Что |
|---|---|
| группа прав | `auth.Group`, один к одному |
| код | латиница, не меняется (`sales`, `claims`, ...) |
| для кого | сотрудники страховой / агенты / платформа |
| видимость по умолчанию | свои / подразделение / вся страховая |
| описание | что умеет, простыми словами |

Предлагаемый каталог (вопрос 1). Действия по договорам и убыткам появятся
вместе с этими модулями; сейчас роль заводится, права в неё добавляются
миграцией каждого модуля.

| Роль | Что делает | Видимость по умолчанию | Есть сейчас |
|---|---|---|---|
| Продажи | оформляет договоры, ведёт своих клиентов | свои | — |
| Андеррайтинг | согласует нестандартные условия, тарифы | вся страховая | — |
| Урегулирование убытков | заявления, расчёт, выплаты по убыткам | вся страховая | — |
| Бухгалтерия | оплаты, комиссии агентов, сверки | вся страховая | — |
| Актуарий и отчётность | только чтение всего, резервы, выгрузки | вся страховая | — |
| Контроль (аудитор) | только чтение всего и журналов | вся страховая | — |
| Администратор справочников | контрагенты, банки, должности | вся страховая | группа есть |
| Администратор интеграций | подключение к ЕРСП | вся страховая | группа есть |
| Сотрудник (базовая) | просмотр справочников | вся страховая | группа есть |
| **Администратор страховой** | пользователи, подразделения, блокировка, сброс пароля — только своя страховая | вся страховая | — |
| Агент | продажи разрешённых продуктов | свои | этап «Агенты» |
| Директор агента | плюс продажи всего агентства | агентство | этап «Агенты» |
| **Администратор платформы** | страховые и их администраторы, состояние; данных страховых не видит | — | — |

### Должность сотрудника (`accounts.JobPosition`, новая, TrackedModel)

Общий справочник для всех страховых (решение 21.10), без страховой в записи.

| Поле | Что |
|---|---|
| название | текст, не повторяется (без учёта регистра и пробелов по краям) |
| порядок в списке | как у других наших справочников |
| действует | снятая должность не предлагается для новых прикреплений, старые остаются |

- Администратор страховой **добавляет** должность — она сразу видна всем
  страховым.
- **Переименовать и снять** — только администратор платформы: переименование
  поменяло бы должность у сотрудников всех страховых.
- Стартовый список — миграцией, по должностям с сайта Mosaic (общие названия
  без названия компании): генеральный директор, заместитель генерального
  директора, главный бухгалтер, внутренний аудитор, директор по коммерческому
  и потребительскому страхованию, андеррайтер, менеджер по коммерческим линиям,
  менеджер по страхованию здоровья и жизни, менеджер по расчёту портфеля
  и резервов, менеджер по урегулированию претензий, менеджер по страхованию,
  ассистент, бизнес-аналитик, директор филиала, начальник отдела, агент.
- Это отдельный список от «Должностей представителей» контрагентов
  (`counterparties.Position`): там должности чужих организаций для ЕРСП,
  здесь — сотрудников страховой. Смешивать — засорить оба выпадающих списка.

### Прикрепление (`accounts.Assignment`, новая, TrackedModel)

Где и кем человек работает с какой даты по какую.

| Поле | Что | Правило |
|---|---|---|
| пользователь | `User` | обязательно |
| подразделение | `Department` | той же страховой, что пользователь; действующее на дату начала |
| должность | «Должность сотрудника» (общий справочник, ниже) | обязательно |
| роли | одна или несколько ролей «для сотрудников страховой» | вопрос 2 |
| руководитель подразделения | да / нет | на дату — не больше одного руководителя на подразделение (проверка в базе) |
| видимость | свои / подразделение / вся страховая | по умолчанию — «вся страховая» (у всех нынешних ролей она такая; когда появятся роли «свои» — по умолчанию самая широкая из ролей); руководитель — не уже подразделения |
| ассистент для | другой пользователь (менеджер) | пусто — не ассистент |
| ассистент видит | все договоры менеджера / только введённые им | только если указан менеджер |
| действует с | дата | обязательно |
| действует по | дата включительно | пусто — по сей день |
| основание | текст (приказ, соглашение ГПХ) | необязательно |

Проверки в базе (`accounts/0005`): «по» не раньше «с»; периоды одного
пользователя не пересекаются (ограничение исключения PostgreSQL на диапазон
дат `daterange(с, по, '[]')`, расширение `btree_gist`); у руководителей
одного подразделения периоды не пересекаются; руководитель видит не меньше
подразделения; «ассистент видит» заполнено тогда и только тогда, когда
указан менеджер; ассистент не сам себе. Триггер `accounts_assignment_rules`:
подразделение и менеджер ассистента — той же страховой, что и человек;
владелец прикрепления не меняется.

Роли прикрепления — отдельная таблица связи; меняются только методом
`Assignment.set_roles()`, который пишет в журнал строку «роли: было → стало»
(названия ролей). Изменения прикрепления видны в «Истории» пользователя
и только его страховой.

Экран (A2.2): блок «Прикрепления» в карточке пользователя — после создания
учётной записи; списки — только своей страховой человека; «периоды
не пересекаются» проверяет весь блок сразу по новым значениям (перевод
в одной отправке: старое закрыто датой «по», новое открыто — проверка
строки по базе ошибочно увидела бы пересечение). В списке пользователей —
«работает сейчас». Подразделение, где работают люди, закрыть нельзя.

Действия на экране:
- **Перевести** — дата перевода, новое подразделение, должность, роли:
  старое прикрепление закрывается накануне, новое открывается с даты.
- **Уволить / завершить** — дата: прикрепление закрывается, учётная
  запись блокируется. Передача портфеля — вместе с договорами.
- Прикрепление, по которому уже есть договоры, не правится — только
  закрывается (появится вместе с договорами).

Права пользователя берутся из ролей **действующего сегодня** прикрепления
(свой способ проверки прав, `accounts.backends.AssignmentBackend`, с A2.3),
а не из групп в карточке пользователя: перевод сразу меняет права, история
ролей сохраняется. Нет действующего прикрепления — нет прав. Группы
в учётной записи действуют только у администратора платформы (у сотрудника
страховой экран их не показывает). Отдельные права учётной записи может
задать только суперпользователь — аварийная мера. Суперпользователь имеет
все права без ролей.

Перенос (миграция `accounts/0006`): каждому пользователю страховой без
прикрепления — прикрепление к головному офису, должность «Не указана»,
с даты регистрации, роли по его группам, основание «перенос прав (A2.3)»;
у кого прикрепление уже есть — группы добавляются к его ролям; группы
сотрудников страховой очищаются. Откат возвращает группы по ролям
действующих прикреплений (поэтому группы после отката могут быть шире,
чем до переноса) и удаляет прикрепления переноса.

## Видимость данных

Одна функция для всех таблиц страховой: «что из этого видит пользователь».

| Кто | Видит |
|---|---|
| видимость «вся страховая» | всё своей страховой |
| видимость «подразделение» | своё подразделение; для филиала — с его отделами |
| видимость «свои» | записи, где он продавец или ввёл их |
| ассистент | плюс договоры своего менеджера (все или введённые им — по настройке) |
| администратор платформы | ничего из данных страховых |
| суперпользователь | всё (аварийная техническая запись, вопрос 4) |

Сейчас действует только первая строка и последние две: договоров ещё нет,
а справочник контрагентов виден всей страховой (вопрос 3). Нынешние
`own_companies` и `get_queryset` в админ-панелях переходят на эту функцию.

## Администратор страховой и администратор платформы

**Администратор страховой** в админ-панели:
- видит и заводит пользователей и подразделения только своей страховой;
  новая запись получает его страховую сама;
- назначает только роли «для сотрудников страховой»; роли платформы,
  «суперпользователь» и чужую страховую выбрать нельзя;
- блокирует, сбрасывает пароль, переводит;
- не может заблокировать или лишить роли последнего администратора своей
  страховой (иначе страховая останется без управления).

Как это устроено (часть A3, решения Бекзода 21.10 — ниже, пункты 11–16):
- **Суперпользователей не видит и не меняет.** Иначе сбросил бы пароль
  суперпользователю своей страховой и вошёл под ним.
- **Себя меняет частично:** свои личные данные и пароль — да; свои роли,
  место работы и блокировку — нет (это делает другой администратор или
  платформа), иначе один человек тихо выдаёт себе любые права.
- **Место работы — только кнопками** в карточке пользователя:
  «Принять» (места сейчас нет: дата, подразделение, должность, роли;
  блокировка снимается), «Перевести» (дата, новое место, роли — по умолчанию
  нынешние; прежнее прикрепление закрывается накануне, его «по» переходит
  к новому), «Уволить» (последний день: прикрепление закрывается этой
  датой; если дата сегодня или прошла — учётная запись блокируется сразу).
  Прямо в блоке «Прикрепления» правятся роли, видимость, руководитель,
  ассистент, основание — смена пишется в журнал «было → стало». Подразделение,
  должность и даты в блоке только для чтения: история места работы
  не переписывается задним числом. Суперпользователь (аварийно) правит блок
  целиком.
- **Вход:** сотрудник страховой без действующего прикрепления не входит
  (уволенный с будущей даты — после неё; принятый с будущей даты — с неё);
  уже открытая сессия такого человека тоже перестаёт действовать
  при следующем запросе.
  Суперпользователь и администратор платформы — без этого правила.
- **Пароль выдаёт система:** при создании пользователя и по кнопке
  «Сбросить пароль» система придумывает временный пароль и показывает его
  администратору один раз; при первом входе человек обязан сменить пароль
  (отметка «сменить пароль при входе»; пока не сменит, другие страницы
  не открываются). В журнале — «пароль: ***», автор — тот, кто сбросил
  (смена своего пароля — сам человек).
- **Новый пользователь — одним экраном:** логин, личные данные, вид
  и сразу место работы (подразделение, должность, роли, дата начала,
  основание). Без места работы сотрудника страховой не создать.
- **Последний администратор:** в страховой всегда есть хотя бы один
  незаблокированный пользователь с ролью «Администратор страховой»
  в действующем прикреплении. Проверяется при блокировке, увольнении,
  переводе и смене ролей — на сегодня и на каждую будущую дату, когда
  меняются прикрепления страховой. Ошибка, только если изменение создаёт
  день без администратора (страховую, где его ещё нет, правило не блокирует).
- Права роли «Администратор страховой»: пользователи и прикрепления
  (смотреть, заводить, менять; удаления нет), должности сотрудников
  (смотреть, добавлять), каталог ролей (смотреть), плюс подразделения
  и журнал (с A1).

**Администратор платформы** (вид «платформа», без страховой, не суперпользователь):
- экран «Страховые компании»: список со счётчиками — пользователей
  (действующих / заблокированных), подразделений, последний вход в страховой;
  из строки — ссылка «Пользователи (N)» на список пользователей этой страховой;
- в списке пользователей — фильтр по страховой, виду, статусу, роли;
- заводит страховую (вместе с головным офисом) и её первого администратора;
- контрагенты, журнал обмена, журнал изменений данных страховых — пусто
  (так работает уже сейчас для пользователя без страховой и без
  «суперпользователя»; закрепим тестом).

Как это устроено (часть A4, решения Бекзода 21.10 — ниже, пункты 17–21):
- **Роль «Администратор платформы»** (код `platform_admin`, для кого —
  платформа) заводится миграцией; даётся группой в учётной записи вида
  «платформа». Права: страховые компании (смотреть, заводить, менять),
  пользователи (в пределах правил ниже), должности сотрудников (смотреть,
  добавлять, переименовывать, снимать), каталог ролей, справочники
  страховщиков и регионов ЕРСП (для карточки страховой), журнал изменений.
- **Администраторов платформы заводит только суперпользователь** (`root`):
  вид «платформа» и группы в учётной записи доступны только ему.
- **Пользователи страховых — вариант «Б»:** в списке платформа видит всех
  (кроме суперпользователей) — логин, ФИО, страховая, вид, «активен»,
  последний вход; фильтры по страховой, виду, статусу, роли. Карточку
  открывает только у администраторов страховых (роль «Администратор
  страховой» в действующем прикреплении) и у людей платформы. В карточке
  администратора страховой: личные данные, блокировка, «Сбросить пароль»;
  место работы, роли, кнопки «Принять / Перевести / Уволить» — нет (ими
  ведает сама страховая). Обычный экран «Добавить пользователя» платформе
  не нужен: администратора страховой она заводит из карточки страховой.
- **Экран «Страховые компании»:** счётчики — пользователи (работают /
  заблокированы), подразделения, последний вход в страховой; счётчик людей —
  ссылка на список людей этой страховой. В карточке
  страховой кнопка **«Завести администратора»**: логин, ФИО, контакты,
  должность, дата начала; место — головной офис, роль «Администратор
  страховой» ставится сама; временный пароль — один раз.
- **Журнал у страховых компаний** (таблица переходит на `TrackedModel`):
  кто завёл, сменил запись ЕРСП, выключил. Строки журнала карточки
  страховой видны её сотрудникам и платформе; платформа в журнале видит
  только таблицы платформы — страховые компании и должности сотрудников.
- **Выключенная страховая** (снята отметка «работает»): её сотрудники
  не входят, открытые сессии перестают действовать; данные остаются.
  Включили обратно — вход открылся.

Тесты на каждое правило — от лица обычного администратора страховой,
не суперпользователя: «чужая страховая не видна», «нельзя назначить роль
платформы», «нельзя сделать суперпользователем», «последний администратор».

## Агенты (этап B)

**Предложено 21.10, решения Бекзода 22–28 — в конце файла. Код — после
подтверждения этого раздела.**

Агент — организация или человек, который продаёт полисы страховой по
соглашению. В системе агент = контрагент из справочника + соглашение
+ место в подразделении + пользователи для входа. Всё — в новом
приложении `agents`, таблицы с журналом (`TrackedModel`), ничего
не удаляется.

```
Агент (страховая + контрагент из справочника)
 ├─ Соглашение            (номер, дата, срок, кто подписал, основание)   — с историей
 ├─ Место агента          (подразделение с даты по дату)                 — с историей
 └─ Пользователь агента   (учётная запись, директор или нет, с даты по дату)
```

Почему не прикрепление (`Assignment`): прикрепление — место одного
сотрудника (подразделение, должность, роли сотрудников). Агентство
прикрепляется к подразделению целиком, а у его сотрудников нет должностей
страховой.

Сейчас — только агенты-юрлица (решение 22): карточки физлица ещё нет.
Агенты-физлица (у Mosaic их 1–2) — после этапа «Физлица», той же моделью:
у агента-физлица один пользователь, он же директор.

### Агент (`agents.Agent`)

| Поле | Что | Правило |
|---|---|---|
| страховая | `InsuranceCompany` | обязательна, не меняется |
| контрагент | `Counterparty` | своей страховой; один контрагент — не больше одного агента в страховой (проверка в базе) |
| счёт для комиссии | счёт этого контрагента (`BankAccount`) | необязателен до модуля комиссий; только счёт своего контрагента |
| работает | — | не хранится: система считает по соглашениям («есть действующее на сегодня») |

Контрагент в архиве — новое соглашение с агентом заключить нельзя.

### Соглашение (`agents.Agreement`)

| Поле | Что | Правило |
|---|---|---|
| агент | `Agent` | обязательно, не меняется |
| номер | текст | обязательно; не повторяется внутри страховой |
| дата заключения | дата | обязательно |
| действует с / по | даты | «по» включительно, пусто — бессрочно; «по» не раньше «с» |
| прекращено | дата последнего дня | пусто — не прекращалось досрочно; не раньше «с» и не позже «по» |
| причина прекращения | текст | обязательна вместе с датой прекращения |
| подписал от страховой | `User` | сотрудник (штатный или ГПХ) своей страховой с действующим прикреплением на дату заключения |
| основание подписи | устав / положение о филиале / доверенность | обязательно |
| доверенность: номер и дата | текст, дата | обязательны при основании «доверенность», иначе пусто (решение 24) |

- Действует соглашение с «с» по «прекращено» (если задано), иначе по «по».
- Периоды соглашений одного агента не пересекаются — ограничение
  исключения в базе, как у прикреплений. Продление — новое соглашение.
- Продукты, процент комиссии и лимиты — отдельная таблица при соглашении,
  вместе со справочником продуктов (не в этом этапе).
- Скан соглашения — когда появится хранение файлов.

### Место агента (`agents.Placement`)

| Поле | Что | Правило |
|---|---|---|
| агент | `Agent` | обязательно, не меняется |
| подразделение | `Department` | своей страховой, действующее на дату начала; любой вид (головной офис, филиал, отдел) |
| действует с / по | даты | периоды одного агента не пересекаются (база) |
| основание | текст | необязательно |

Перевод — кнопкой, как у сотрудников: старое место закрывается накануне,
новое открывается с даты; подразделение и даты в записи только для
чтения. Подразделение, где есть агенты сегодня или с будущей даты,
закрыть нельзя (правило дополняет нынешнее «где работают люди»).
По этой таблице номер договора возьмёт код подразделения на дату продажи.

Куратора (закреплённого сотрудника) у агента нет (решение 26).

### Пользователь агента (`agents.Member`)

| Поле | Что | Правило |
|---|---|---|
| пользователь | `User` вида «агент» | своей страховой; не меняется |
| агент | `Agent` | своей страховой; не меняется |
| директор агента | да / нет | видит все продажи агентства; обычный сотрудник агента — только свои |
| действует с / по | даты | у одного пользователя периоды не пересекаются (база) |

- Пользователя агента заводит страховая из карточки агента: логин, ФИО,
  телефон, директор или нет, дата начала; временный пароль выдаёт
  система (как у сотрудников, `issue_temporary_password`).
- Отключает его тоже страховая (решение 28), кнопкой «Отключить» с датой
  последнего дня: дата сегодня или прошла — учётная запись блокируется
  сразу. Сам директор агента своих людей не отключает (кабинета пока нет).
- Вид «агент» убирается с обычного экрана «Пользователи»: сейчас там
  можно завести «агента» с прикреплением к отделу и ролями сотрудника
  страховой — это ошибка, агент заводится только из карточки агента.
- Роли «Агент» (видимость «свои») и «Директор агента» (видимость
  «агентство») — в каталоге ролей, для кого — «агенты»; у пользователя
  агента роль задаёт отметка «директор». В перечень «видимость»
  добавляется «агентство». Права в эти роли придут вместе с договорами.

**Вход агента** — только если одновременно: учётная запись не
заблокирована, страховая работает, у пользователя есть действующая
связь с агентом, у агента — действующее соглашение. Соглашение
закончилось — вход закрывается сам, без ночных заданий; «Прекратить
соглашение» с датой сегодня или в прошлом блокирует пользователей агента
сразу. Кабинет агента и ввод продаж — вместе с договорами (решение 23);
до тех пор агенты в систему не входят (в админ-панель их не пускает
`is_staff`), а правило входа проверяется тестами.

### Кто работает с агентами

- Новая роль сотрудников страховой **«Работа с агентами»** (код `agents`):
  заводит агентов, соглашения, места, пользователей агентов; прекращает
  соглашения, отключает пользователей. Удаления нет.
- В Mosaic её получают директоры (руководители) отделов (решение 27);
  назначает администратор страховой в блоке «Прикрепления».
- Администратор страховой — те же права (агенты входят в «всё своей
  страховой»).
- **Видимость агентов** (решение 25) — по месту агента на сегодня:

| Видимость сотрудника | Видит агентов |
|---|---|
| вся страховая | всех агентов страховой |
| своё подразделение | у кого место сегодня — его подразделение; у руководителя филиала — и отделы филиала |
| свои | никого (куратора нет) |

  Это первая таблица, где работает видимость «подразделение»: функция
  «что видит пользователь» пишется общей, потом к ней подключатся договоры.
  Агент без места на сегодня (место закончилось, новое не открыто) виден
  только при видимости «вся страховая».
- Администратор платформы агентов не видит — 403 (тест, как
  в `accounts/test_platform.py`).

## Решения Бекзода 21.10

1. Каталог ролей — как в таблице «Роль».
2. Место одно (подразделение, должность), ролей у прикрепления может быть

5. Код подразделения необязателен (в Mosaic нет, в Inson есть). Регион
   у филиала обязателен.

Решения по части A3 (21.10):

11. Учётная запись Бекзода разделяется в конце A3: аварийный
    суперпользователь `root` без страховой заводится командой на сервере,
    у `bekzod` снимается «суперпользователь» — он работает как администратор
    Mosaic по своим ролям. Запись администратора платформы — в A4.
12. Свои роли, место работы и блокировку администратор страховой не меняет;
    личные данные и пароль — меняет.

    «Принять», «Перевести», «Уволить»; роли, видимость, руководитель,
    ассистент, основание — прямо в блоке.
14. Увольнение — датой последнего дня; сегодня или в прошлом — блокировка
    сразу; без действующего прикрепления сотрудник страховой не входит.
15. Временный пароль придумывает система, показывает один раз; при первом
    входе — обязательная смена (вариант «А»).
16. Новый пользователь заводится сразу с местом работы.
